## Interfaces and behavior

### Task, runtime choice and component boundary

Recommend one fictional Little Hearth Bakery Mon–Fri corporate lunch-box trial: **A Offer planner** develops an offer brief; **B Operations planner** uses A's exact committed brief for a substantive fulfillment/launch plan. PM owns the fixture/rubric. Fixture v1: SGD14/box, variable SGD9, minimum contribution SGD4; chicken-and-vegetable or vegan-and-vegetable variants without allergy/nutrition assurance; minimum10/order, maximum30/day;150 staff-minutes/day, fixed30 +4/box; prior working day15:00 cutoff,11:30 dispatch,12:00–12:30 target, one route. Six fictional contacts: four interested in20-box orders and two undecided, no booked orders. Recommended20/day consumes110 staff-minutes and yieldsSGD100 daily contribution; interest is not demand commitment. No supplier/order/customer system or external action is connected.

Recommend direct first-party **Anthropic Messages API**, pinned **`claude-haiku-4-5-20251001`** for both independent role executions, standard global text requests. Current official documentation lists that snapshot,200k context,64k model maximum output and $1/M input / $5/M output. Our call maxima are much lower. Inference: inexpensive bounded text planning makes Haiku a practical first evaluation candidate; useful bakery output remains unproven. Two roles mean two separate fresh provider requests, participant IDs and attributable receipts, not two labels on one response. Distinct providers are unnecessary.

Alternative: same-provider Sonnet5.5 offers a higher-capability candidate at currently documented $2/M input/$10/M output, but would require a revised approved ceiling/model assessment. Historical external Codex is a later BYOA path with different runtime/account assumptions, not an automatic fallback. Unsupported snapshot/account, changed rate or insufficient allowance blocks execution; never substitute a model, provider, personal subscription or historical Claude budget silently.

Use a **separate server-side Node worker process** (`runtime-workers/native/`), operated by platform operator for the prototype. World never loads the provider adapter. Worker consumes a versioned runtime-neutral protocol via loopback HTTP with Session-scoped machine capabilities; it owns provider HTTPS, request serialization, local durable dispatch journal, response validation and usage receipts. Same protocol later supports external runtimes; customer pairing/launch is absent from native onboarding. The separate process is a credential/dependency boundary, not a claim of OS isolation from another process under the same local account.

Operator provides a dedicated company/development-funded provider project credential only to the worker's launch environment after separate authority. World process receives an explicit allowlisted environment without the key; no browser, domain record, prompts, arguments, source, analytics, crash dump or raw error log contains it. No inherited environment dump. Worker reads no World SQLite or employee directories, offers no shell/filesystem/network tools to the model, and makes outbound requests only to the fixed provider host with redirects disabled. Provision/rotate/revoke credentials out of band; account identity is an opaque operator-managed reference, never the secret. A restricted service identity/secret vault and retention review are production-readiness work before private SME use; same-user local operation uses fictional fixtures only. Stop/request abort cannot recall disclosure or prove provider cancellation/erasure.

### Public ports, scope and wire contract — proposed v2

| Owner | Public responsibilities |
| --- | --- |
| `agents/connection` | Native role descriptors, operator/runtime binding, capability authentication/readiness/revoke. No provider call or key. |
| `work/session` | Prepare/start/stop/get; immutable snapshots, grants, A→B scheduling, work/attempt correlation and reservation admission through accounting port. |
| `collaboration/document-review` | Commit attributed contributions, create/edit proposals, feedback, human acceptance. Acceptance transaction port covers expected note revision, note revision, receipt and closed grants together. |
| `work/usage` (new cohesive feature) | Test funding account, allowance authority, rate basis, reserve/mark-dispatched/settle/reconcile and safe per-call/task views. No real payment/credit sale. |
| `platform/sqlite` | Repositories and narrowly named transaction ports; no provider orchestration or domain scheduling. |
| `runtime-workers/native` | Protocol client, durable one-shot journal, fixed Anthropic adapter, request/output/deadline limits, usage report. May depend only on versioned shared wire contracts, never feature internals. |

Proposed HTTP operations: authenticated owner `prepare/start/continue-to-operations/stop/list/get`, disclosure and funding/usage views, proposal edit/request-changes/accept; machine `claim/ack/status/result/failure`. `continue-to-operations` requires the exact committed A contribution ID/revision/hash, current grant epoch and owner command key; identical replay returns its receipt and conflicting payload rejects. Owner cookies cannot authenticate a worker; worker capabilities cannot invoke owner APIs. Bind capability verifier to generated runtimeInstanceId/participantId/operatorId/worldId/sessionId/epoch, maximum15-minute expiry, exact allowed actions; native supervisor provisions each A/B capability internally, never in UI. Readiness means configured protocol worker available; provider account/model entitlement is not proved by that status.

Strict schemas reject unexpected fields, unsupported required capabilities/version, malformed UTF-8 and excess bytes. Server derives identities from authentication; body labels cannot confer authority. Every work envelope carries `protocolVersion=2`, IDs (World,Session,participant,work,attempt,operator,fundingAccount,allowance), grant epoch, purpose/role, immutable `noteId/revision/bodyHash/body`, permitted recipients/actions, exact role/template revision, deadline, call/token/byte limits and rate-basis ID. B adds A `contributionId/revision/bodyHash/body`. Digest the canonical serialized complete envelope. Disclosure renders those same payloads before start, including that B's A-dependent content is available only after A commits. Use no personal memory, unsaved edits, whole-World search or unselected resources.

Results carry attempt/envelope digest/epoch/event ID, provider request/message IDs, requested/reported model, bounded plain-text body, exact source/dependency provenance, stop reason, usage quantities and provenance, terminal outcome. World assigns contribution IDs after transactional authorization. An identical repeated event returns its existing receipt; same ID/different digest rejects. Unsupported blocks/tool requests or truncated `max_tokens` outputs are retained as incomplete, not silently repaired by another call or offered as complete cooperative work.

Effective access is platform ∩ World ∩ operator ∩ Session ∩ resource ceilings; denial wins. A can receive selected note and contribute brief. B can receive that note and specifically authorized committed A brief and contribute plan. Neither can create Sessions, enlarge context, change funding, edit canonical note, accept, order products or cause additional calls. Prompt injection cannot modify server grants. Snapshot is frozen at prepare; start never recaptures new note contents. Later human save shows divergence; reselecting input requires a new prepared scope/epoch/explicit review, preserves old evidence and does not reset attempts or money.

### Persistence and lifecycle

Proposed v2 tables with UUID primary keys and foreign keys: `agent_bindings` (operator/runtime/participant identity and credential verifier/expiry), `participation_sessions` (World, owner, purpose, status, epoch, funding/allowance), `session_snapshots` (note revision/hash/body), `work_items` (A/B/dependency/status), `work_attempts` (unique work+ordinal, envelope digest, deadline, dispatch state), `contributions` (immutable body/hash/author/attempt/source; unique attempt), `proposal_revisions` (unique proposal+revision), `proposal_feedback`, `acceptance_receipts` (unique owner+commandKey, payload digest, note resulting revision), safe `work_events` (unique attempt+eventId). Note and World schemas/IDs remain unchanged.

Prepared → running A → awaiting brief confirmation → running B → awaiting review; failed/stopped/expired/indeterminate are distinct terminal execution states. Work result/receipt and human acceptance are distinct. After A commits, automated eligibility checks require a terminal complete response, valid plain-text structure, matching provenance/digest, required brief sections and byte/token/attempt limits. Those checks do not guarantee semantic validity. The owner inspects the immutable A brief against the fictional fixture and PM rubric, including scope, arithmetic/capacity, assumptions and absence of invented bookings, then chooses **Continue to operations plan** only if it is suitable. Infeasible or out-of-scope A remains retained; B stays blocked, and stopping consumes no B call. This checkpoint neither accepts canonical work nor edits A nor authorizes extra inference.

Persist an owner continuation receipt bound to A's exact contribution ID/revision/hash and grant epoch. B is offered only after that receipt, automated eligibility and a transactional recheck of current scope, authority, sharing permission, funding reservation, selected rate basis and deadline. B receives the exact confirmed A artifact; neither confirmation replay nor changed source can dispatch a second B. Both A/B maximum reservations were held at start. Waiting for the owner counts toward the same 240-second task deadline; the checkpoint does not reset or extend it. On expiry, close execution and release B only with positive evidence it was never dispatched, preserving A and any unknown A-cost hold. No late continuation, retry or refreshed attempt follows automatically. A failure blocks B; B failure retains A. No invented dependency or synthetic second agent. Initial B plan seeds an editable proposal; feedback or human edits trigger no inference. A later revision run needs fresh explicit authority/attempts.

Stop transaction increments epoch/revokes capabilities/blocks claims and results before sending worker abort. Commit racing stop is ordered by SQLite transaction. Already-dispatched cost may remain due; stop is not a refund. Restart invalidates active capabilities/epochs and marks unresolved dispatched work indeterminate; worker reserved/dispatched journal never reruns inference automatically. Cached transport response resend is allowed only under current authority, same attempt/digest; settlement reconciliation has a separate narrow receipt port that cannot commit late content. Owner reviews retained work after end/restart without reviving grants.

Acceptance takes authenticated owner, World, proposal ID/revision, expected current note revision, command key and final edited text. One SQLite transaction checks ownership/proposal/source, saves next note revision, stores immutable acceptance receipt and ends grants. Duplicate identical command returns original receipt; changed payload rejects. Stale note/proposal conflicts without overwrite. Owner may accept retained complete B proposal after end subject to current revision; incomplete salvage is not labeled successful A→B cooperation.

### Funding, usage and concurrent reservation invariants

Requester/employee, agent/role, runtime/operator and company funding account are different identities. Prototype account is explicitly **test company funding / development allowance**, no real company balance or purchased credits. Bind fundingAccountId, providerProjectRef, payerRoute and approved allowance ID to task/attempt before dispatch; never select personal funds when insufficient. Raw provider expense is USD; fictional bakery economics are SGD; no currency conversion or retail charge is selected.

Additional tables: `funding_accounts` (test flag/company label/route), `execution_allowances` (approved authority reference/currency/call/task/concurrency ceilings), `price_bases` (provider/model/route/global standard/rates/effective+verified dates/source URLs/hash), `usage_reservations` (unique attempt, maximum microUSD/state), `provider_calls` (unique attempt/inference ordinal, request identity/serialized digest/dispatch journal receipt), `usage_reports` (deduplicated report provenance and input/output/cache/tool quantities), `settlements` (unique providerCallId+chargeKind), `reconciliation_events` (append-only correction/evidence/actor). Persist integer microUSD, never float arithmetic or arbitrary credits. Retain raw provider-reported counts and computed estimate separately from provider-invoiced expense; missing usage has explicit unknown status.

1. `BEGIN IMMEDIATE` validates authority, current grant/deadline/model/rate, account/allowance binding, available allowance (cap minus settled minus all held reservations), task count and global/account in-flight cap. Atomically create one attempt/reservation and dispatch permit. No network request inside SQLite transaction. Reserve both A/B maximums at owner start so future B capacity is not competed away; B reservation remains non-executable until A commits. Concurrent starts cannot spend the same availability.
2. Worker fsyncs exclusive journal with immutable attempt/request digest before inference and confirms permit. Mark dispatch-intent durably before sending. Crash between intent and send is uncertain, not definitely free. Lost ack does not permit second inference. SDK retries are disabled (or use built-in fetch with one send); no429/5xx/network retry, redirect, failover or tool loop.
3. Validate terminal usage against selected rate basis and bounds; transaction settles each compute charge once and releases only unused portion. Same report is idempotent, conflicting report quarantines. Provider billed input/output/cache/tool quantities are never double counted. Unexpected usage exceeding reservation freezes account/allowance and records discrepancy; no optimistic truncation or negative balance.
4. Pre-send validation failure with positive journal evidence of no dispatch can release reservation while retaining consumed attempt. Any timeout/disconnect/crash/ambiguous error or missing/partial usage retains full uncertain reservation, even if body arrived or provider said error. No expiry/restart automatically releases it; B blocked if required precursor evidence is uncertain. A never-executed B reservation can be released after terminal A with proven no B dispatch. Funding availability does not reset on new chat/task/process.
5. Narrow operator reconciliation appends provider usage/billing or provable no-dispatch evidence, adjusts hold/estimate once with unique reconciliation key and reason, retains original history. No full request/body/key log. Task totals distinguish provider-reported/computed-estimated/invoiced/held-unknown; unknown is not zero. If exact provider evidence cannot be obtained, retain hold and label unresolved, no manual assumption of zero.
6. Company-direct BYOA compute is informational external expense, never debit native compute again. A separately agreed platform service charge would have a distinct charge kind/authority; none selected now. No double compute, personal fallback, paid credit issuance or commercial pricing follows from this prototype.

Legacy historical $1 allowance remains entirely separate and unchanged. A new authorization must identify a new isolated provider project or explicitly reconcile shared-project earlier usage/holds before activation; uncertain historical shared usage cannot be hidden by seeding a fresh zero ledger. Original totals remain visible as legacy, not recharged.

Expected admission-envelope price at current standard rates is `(4000+6000)×$1/M + (1500+2000)×$5/M = $0.0275`, an indicative upper estimate for those counts, **not an enforceable billed-input guarantee**. Official token counting calls its count an estimate. Byte limits likewise are not a provider billing contract. Conservative exposure instead uses the selected model's documented **200,000-token context ceiling for each input**, without subtracting output (over-reservation), plus our hard generated-output caps: `2×200000×$1/M +3500×$5/M = $0.4175`; round allowance upward to $0.42. Reserve the conservative amounts even though fixture should be much smaller. If current route billing includes charges outside that standard token basis, cannot verify the model ceiling, changes price/endpoint, enables caching/tools, or exposes a wider context mode, fail closed and revise before execution. Taxes/account-wide charges are not native compute; account purchase/tax authority is absent. A timeout is an operational limit, never proof of zero cost or cancellation.

Reverify model availability, rates, no-extra-charge configuration and context/output contract from official sources immediately before a separately authorized run; no authenticated capability preflight now. Failure or truncation stops the single task without using remainder for retries. Human review/acceptance remains a separate real user action. Record requested snapshot versus returned model; aliases are not permitted fallback. Haiku's current documentation promises no retirement sooner than2026-10-15, not guaranteed indefinite availability; route assessment expires when execution is scheduled later or material docs change.
