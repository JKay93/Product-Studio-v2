### Failure and stop contract

Any count/provider/storage/timeout/validation failure ends that attempt without another send. `max_tokens` is incomplete; retain its evidence, block complete-quality claims and dependent B. A failure blocks B; B failure preserves A for explicitly labelled partial review. Stop closes future claims/dependent admission and increments grant epoch before best-effort abort. A stop does not prove provider cancellation, forgetting or refund. Commit-versus-stop ordering must be transactional. After dispatch intent, uncertain send/response or restart remains unknown with reservation held. B may release only with positive proof it was never dispatched. Late results may support accounting reconciliation, never write canonical content or activate B. Cached receipt recovery may resend an identical result under valid current authority; it must never call inference again.

## Approach and dependencies

The offline candidate currently blocks actual activation at `runtime-workers/native/start.ts` and `NativeWork.start(false)`. The database explicitly requires synthetic Sessions/test funding; usage, reconciliation and rate binding are hardcoded test-only. **Fixing journal/transport reliability does not complete the live path.** A later approved activation needs an explicitly bounded reviewed composition that binds the actual allowance/account/rate/provenance, provisions private machine capabilities and invokes the provider transport. It cannot bypass current holds by setting `synthetic=true` and relabelling receipts.

Use a dedicated isolated test store for eventual live work, with a reviewed additive live-compatible persistence contract and new allowance identity; do not migrate the original foundation to run this test. Keep test/live accounting clearly separated while checking any shared provider-account exposure. The activation design and affected tests must be reviewed before loading a real credential. The eventual authorization should permit that bounded activation implementation plus its explicitly specified preflight/run; until then the worker startup stays disabled.

The runtime alone loads the provider secret from the approved launch environment after authorization, retains it only in memory and sends it only to the fixed HTTPS provider host; World/browser/domain records/prompt/log/evidence receive neither key nor provider auth header. No credential extraction, broad environment dump, personal memory or global setting change. Owner cookie and private per-attempt machine capability remain separate credentials. HTTP redirects, SDK retries and account fallback are disabled. A future explicit launch must name its exact route/process/test-store/allowance and require user Start rather than unattended polling/service operation.
