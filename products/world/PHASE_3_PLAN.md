# Phase 3 — Real identity, persistence and authority

This is the technically reviewed implementation proposal requested on 2026-10-04, ready for the user's review. It preserves approved product decisions; backend work has not started. The accepted Phase 2 shell remains the interface. Current app baseline is MyWorld aa8771c3e663a0dfef95847f90c23420d0e88804.

## Outcome [world:phase-3:outcome]

A real user signs up, creates their persistent personal Agent, returns later and finds it intact. They can work in a personal World and authorized organization Worlds, with separately stored Sessions and drafts. They can inspect relevant access grants and memory ownership. Removing membership or a grant blocks further protected access while preserving personal continuity and authorized organization records.

Phase 3 establishes the trustworthy foundation for doing work. Model responses, meeting extraction, task execution and the worker arrive in Phase 4; real sub-Agent execution and consequential approval opt-out arrive in Phase 5. The full portable-learning and departure experience remains Phase 6. Basic separation/revocation is required now, not deferred until those phases.

## Boundary [world:phase-3:scope]

In: Supabase Auth/PostgreSQL; schema/migrations and RLS; real users, Agent ownership, personal/organization Worlds and memberships; persisted Sessions, user messages/drafts and Agent selection; scoped standing grants; personal/World text memory records with source ownership; revocation and organization retention; audit and integration checks. Minimal create/join/manage-World controls reuse existing dialogs and navigation.

Out: provider calls, automatic learning, background jobs, real delegation, external effects, actual approval opt-out execution, portable exports/imports, integrations, Incubator, billing and production deployment. Do not expand infrastructure. Do not expose an operational-looking mock action as a real backend effect. Keep the mock experience explicitly available for demonstrations/tests; backend mode must never silently fall back to sample identities or bypass denied access.

## Data and ownership [world:phase-3:data]

Proposed logical records, with exact migrations resolved during 3.1:

| Record | Essential boundary |
| --- | --- |
| Profile / World / membership | Stable user IDs, personal or organization World, explicit role/status, authority version; unique personal-owner constraint and atomic bootstrap. A member list is not a resource-access grant. |
| Agent / World participation | Exactly one personal-user or organization-World owner, enforced by explicit XOR check; organization owner must be an organization World. Primary personal Agent unique per user, extra Agents allowed; creation retry key prevents duplication. Participation (World ID, Agent ID) separates use from ownership. Private configuration is separate from safe identity/effective-World projections. |
| Session / participants / messages / drafts | Session has one World; explicit access policy/participants. Server sets author and provenance. Draft unique (Session, Agent, author) with revision; messages have author-scoped idempotency key. Composite foreign keys bind Session/messages/grants to same-World Agent participation and prevent ID substitution. |
| Standing grant | Issuer, authorized recipient/acting identity, target Agent/resource, World, Session or explicit bounded Session set, capability, status/expiry/revocation/version. No implicit wildcard scope. |
| Personal memory / World knowledge / source links | Owner/World constraints cannot both be absent. Source and derived-record ownership are retained; using an Agent grants no access to its personal memory. |
| Audit event | Server-authorized actor and scoped event for membership/ownership/grant/revocation changes. Organization-visible metadata excludes personal memory and private chat payloads. |

Proposed first roles: owner/admin manage their World within delegated limits; member accesses permitted work; organization archive review is an explicit capability, not a consequence of being a member. The exact role-to-capability mapping is a Phase 3 implementation proposal, not a new product guarantee. For organization Sessions, authorized review of World work coexists with participant access; personal Sessions remain private. New invitations must be bounded, expiring and resistant to replay/role substitution. Automatic invite-email delivery is outside setup authority until configured.

Draft save uses compare-and-swap against an expected revision and returns a visible conflict rather than silently overwriting another tab. appendMessage receives a client request ID and the exact draft revision; one transaction appends once and clears only that revision. A retry returns the existing result and never deletes a newer edit. Organization reviewers see submitted World messages, never author-private drafts. Do not persist an entire Session as a last-write-wins JSON object.

## Enforcement and revocation [world:phase-3:enforcement]

Derive the actor from validated server authentication. Resolve World, membership, ownership, Session and grant from current records. Never trust browser-supplied user/owner/role fields or an ID alone. Use one typed authorization policy interface for API/application services; PostgreSQL constraints/RLS independently protect caller-scoped data access. Avoid adding a generic policy engine/service.

Use request-scoped @supabase/ssr clients and Next 16 proxy cookie refresh, preserving refresh cookies/headers. Verify identity with getClaims; do not use getSession's cookie user as proof. Use getUser where fresh Auth user status is required. Personalized responses remain uncached by shared infrastructure; no shared server client carrying another user's session. Implementation must check the installed Next guides before coding. [Supabase's Next.js server-client guide](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs) supports this authentication/cookie boundary.

Use authenticated caller-scoped database access for ordinary requests. Isolate any necessary privileged bootstrap/admin path behind narrowly scoped server code; service-role access is not protected by RLS. Do not pass privileged keys to the client. Role/membership truth lives in database records, not only stale token claims. Session resource permissions remain separate from World membership, and Agent ownership remains separate from participation. Revoke unnecessary database grants, use safe invoker views, and restrict any required definer function's execution/caller binding with a pinned search_path. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) describes stale-claim and privileged-access limits.

Revocation is a transactional state change, not merely logout or hiding controls. Proposed protected mutations use authenticated RPCs; revoke ordinary direct INSERT/UPDATE/DELETE paths that could bypass serialization. Where definer write functions are needed because caller table writes are revoked, they must derive the actor, enforce current policy and expose only narrow commands. Each mutation acquires relevant membership/grant/owner-policy row locks in a fixed order (FOR SHARE), then rechecks status/version; revocation updates the same rows, increments versions and audits atomically. If mutation wins the lock it commits before revocation; if revocation wins, the subsequent mutation sees revoked state and denies. A plain RLS subquery plus earlier server precheck is insufficient. Test both barrier-controlled interleavings through permitted RPCs and denied raw-write paths. [PostgreSQL documents RLS policy-subquery races](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) and [row-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html).

New reads begun after revocation commits must deny; already-running snapshots or returned data are not claimed recalled. Version stamps detect stale queued/request context; future workers recheck at dispatch, resume and effects. Phase 3 proves real database access/mutation revocation and defines the worker contract; it does not claim cancellation of nonexistent jobs. Keep database transactions short, without external provider/network effects.

Clear affected client state on logout/revocation and partition requests/cache keys by user, World, Session and Agent; cancel or discard stale in-flight UI responses. Personal drafts are author-private even inside organization work. Retained submitted messages/records remain available under an explicit world.review capability; membership revocation does not cascade-delete personal identity or World archives. Exact retention duration remains an approved open choice. No exported learning is produced yet.

Minimal provenance records immutable server actor, owner scope, World/Session/source IDs and source version. Reject organization-source links into personal memory and cross-World derived links. Standing-grant CRUD records future permitted delegation; it does not execute another Agent or expose private configuration. Do not create an automatic-learning/export framework in this phase.

## Reuse and folders [world:phase-3:organization]

Keep src/app thin: authentication UI, callback/request entry points and composition. Domain policies/contracts belong in public interfaces under src/modules/agents, worlds, sessions, authority and knowledge; add an identity module only for its implemented responsibility. Supabase/auth/storage SDKs and server-only client factories belong in src/adapters. Migrations/policies/fixtures belong in supabase; integration and browser journeys in tests.

Replace the mock dependency through a client-safe WorkspaceView and explicit async commands: createAgent, createSession, saveDraft, appendMessage, switchScope and revokeAccess. Commands use typed scope IDs, expected revisions and request IDs; the controller composes demo/server repositories. Replace fixed personal/acme/bcme WorldId sample unions and ownership comparisons against display strings such as You with stable opaque IDs and explicit owner descriptors. Generic React setters and updateSession(transform) are not backend APIs. This extraction is prerequisite work, not a drop-in adapter swap.

Reuse existing sidebar/forms/chat components rather than creating a second UI. Keep async loading/errors/denied/revoked states explicit. No framework/SDK imports in domain policy. Preserve canonical Button/Dialog/QuickMenu, sidebar sizing, composer behavior and Calm Fluent. Add directories only as used; do not prepopulate empty service layers. No queue/worker/provider dependencies in this phase without a concrete need.

## Proof matrix [world:phase-3:proof]

| Check | Required proof |
| --- | --- |
| Real persistence | New account/Agent/World/Session, message and draft survive reload and a new authenticated browser context. Concurrent bootstrap/primary creation, stale draft saves and append retries cannot duplicate identity/messages or delete newer drafts. |
| Identity/session | Unauthenticated/invalid identity is rejected; logout clears client/private state; another account never inherits selected data/drafts. Authentication is distinct from World authority. |
| World/resource isolation | User B and wrong/unknown World/Session/Agent IDs cannot access A's private resources through API, direct database or forged relationships. Test user in both organizations, user in only one and authorized reviewer. |
| Standing access | Issuer authority, recipient/action/Session limits, expiry, revoke and owner restrictions enforced. Configuration/private memory cannot be reached through a borrowing grant. |
| Revocation/races | Existing authenticated client + concurrent operation + stale grant/version all fail after revocation commits; no cached UI resurrection. Previously completed reads are not claimed recalled. |
| Memory/retention | Personal owner correction works; org reviewer reads only permitted World records; personal/private harness data excluded; no portability without future authorization/acceptance flow. |
| Database constraints | Owner-null/both-owner records, cross-World references, forged roles and bypass attempts denied. Verify through real authenticated database access, not only a service-role fixture client. |
| UI regression | Accepted signup/Agent creation, navigation/search/resize/menu, scope switching, composer and mobile focus retained. Demo/test adapters remain explicitly distinguished. |

A Phase 3 PASS requires authenticated API and direct-database evidence plus independent review. A green mocked policy test alone is insufficient. Private-storage isolation must be proven before file upload/retrieval is enabled; text records suffice for the initial slice.

## Setup decisions and readiness [world:phase-3:setup]

Choose during implementation setup: a dedicated development/test Supabase project versus a local Supabase stack; access method and approved cost boundary; authentication method and confirmation/redirect/mail configuration. Recommendation: email/password for the first slice in a dedicated nonproduction environment, confirmation/redirect behavior explicitly configured there, no social-provider sprawl. Test fixtures use controlled identities; this plan assumes no existing account, SMTP service or local runtime. If local prerequisites are unavailable, identify that before treating local setup as ready. Never reuse production data for destructive verification.

Use existing authorized resources where available. Creating a project, installing runtime tooling, obtaining secrets, sending mail or spending money is not accomplished/authorized by this planning document. Credentials stay in approved secret/environment configuration, never product docs. Public configuration examples may list variable names only. Model/provider/hosting choice is not a Phase 3 blocker because no inference or publication occurs.

Implementation can begin with contracts/schema/tests before remote secrets; the authenticated end-to-end milestone requires a working chosen database/Auth environment. Keep that as an explicit setup dependency, rather than secretly falling back to mocks. No calendar estimate or production-release claim is made.
