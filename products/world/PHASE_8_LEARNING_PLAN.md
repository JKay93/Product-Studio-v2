## Outcome and current foundation [world:req:phase8-outcome]
An Agent should become more useful through remembered preferences and verified lessons. Users can see why a memory exists, correct it, stop its future use and control where it applies. Work across Worlds preserves private personal continuity, current jurisdiction and organization-owned information. Leaving an organization stops its access/work while retaining authorized personal continuity and organizational archives.

The central loop is **work → feedback/results → propose a useful lesson → review/adopt → apply in future work → evaluate and refine, replace or retire**. It operates while users remain in their personal and organizational Worlds, across new Sessions and repeated work. Learning triggers do not depend on resignation, offboarding or a portability request. Leaving is a separate access/continuity event; it is not when learning begins or when ordinary memory adoption becomes available.

Historical foundation before Phase 8 saved deliberate personal/World memory through `world_save_memory` with revision checks, same-scope source references and audit. Corrections overwrote current text; complete immutable memory-text history, durable stop-use, persisted suggestion activation and export approval were absent. The worker compiled configuration, chat history and Knowledge passages but did not retrieve saved memory. Personal configuration and foreign source-organization configuration were excluded from organizational execution. Memory suggestions/forgetting/portability in parts of the UI were local/demo behavior. The implemented memory-v1 contract and verified behavior supersede this baseline as described in the report.

Current sources: `World/src/adapters/database/personal-repository.ts`, `World/src/ui/patterns/saved-knowledge.tsx`, `World/src/ui/patterns/agent-memory-settings.tsx`, `World/src/adapters/worker/input.ts` and migrations005–010/022/031. Existing `source_id/source_version` refer to another memory record, not a Knowledge passage or job. The plan adds typed provenance rather than pretending those fields already prove every origin. Current World-memory reads include current members; restricted suggestions need their own explicit authorization before publication.

## Recommended product choices [world:req:phase8-defaults]
Accepted recommendations for this implementation; current runtime behavior changes only through reviewed implementation and verification.

| Choice | Recommendation | Reason |
| --- | --- | --- |
| Learning mode | Start with **Suggest**, with an **Off** option. Explicit owner-authored memory can be saved directly through an authorized UI action. Inferred suggestions need deliberate acceptance; automatic activation is deferred. | Useful accumulation without silent personality changes or turning every chat into an approval task. |
| Learning triggers | Explicit corrections and completed useful work are candidates. Use deliberate checkpoints; do not run a separate extractor after every message. | Avoid latency, duplicate suggestions and unnecessary cost. |
| Adoption notification | A small nonblocking notice offers review/adoption of a persisted suggestion. Reuse Notifications and existing review controls; ordinary work continues. | Makes ongoing learning visible without requiring users to browse settings or interrupting every task. |
| Personal use in other Worlds | Personal-only by default. The owner may explicitly share selected non-sensitive working preferences with named Worlds. | The current privacy boundary must not be replaced with unrestricted personal-memory loading. |
| Organizational learning | Derived from organization work stays World-scoped by default. Authorized World owners/admins with access to the evidence control activation/publication of shared World lessons. | The model cannot declare company information personal or safe to export. |
| Portable learning | Organization release of the exact selected text, followed by user acceptance. No blanket export permission in this first implementation. | A generalized lesson can still contain confidential information. |
| Removal | “Stop using” takes effect immediately for future admission and pending dependent work; correction creates a new version. Storage purge/retention remains a separate decision before pilot. | Clear user control with audit/history and honest deletion semantics. |

Memory changes do not alter Universe/World/Agent-owner/Session permissions, tools, budgets or approval floors. A remembered workflow is guidance about how to work, not authority to perform an action.

## Memory lifecycle and ownership [world:req:phase8-lifecycle]
Proposed flow: **observation → suggestion → notification/review → explicit adoption → active memory → application/feedback → corrected or retired**. The Agent has identified a proposed lesson at the suggestion stage; it has not yet adopted it. Dismissal/rejection leaves it inactive without affecting ordinary work; the same candidate should not repeatedly reappear. Direct owner-authored entries use the same validation/version/audit path without needing a model to infer them.

Each active record has a stable identity, owning user or World, intended Agent/use scope, type (preference, workflow lesson or factual context), immutable text revisions, state, origin, creation/decision actors and timestamps. Suggested evidence and uncertainty are visible during review. Model confidence is advisory, never an authorization check. Types do not permanently rewrite Agent personality or skills.

Typed provenance records exact originating message/job, permitted Knowledge item/version/passage, memory revision and contributing Agents where applicable. Server code stamps origins and ownership from actual admitted inputs; the model cannot invent authoritative source IDs, approve itself or choose a more permissive namespace. Derived records inherit their sources' restrictions until an explicit authorized scoped World publication or portable release creates an independent permitted lesson. Avoid requiring every memory to be re-approved merely because unrelated source data changes; invalidate affected records/jobs using their exact dependencies.

Personal candidates/records are visible only to their owner and admitted runtime paths. Unowned Agent inspectors have no private-memory management. Organization candidate review respects the originating Session and current resource visibility; World admin status alone must not expose a restricted Session. Published World lessons can be read by authorized current members. An admin needs access to the relevant evidence before approving it. Organizations inspect the effective shared configuration and their own candidates/releases, never all private personal memory.

World publication is a distinct exact-version decision by an authorized World owner/admin who currently has access to the evidence. They select the lesson text, named World audience and permitted use scope, consciously releasing that text to the audience. This permits a selected published lesson to be used without admitting its underlying restricted Session/document. The publication receipt and original evidence retain provenance; underlying titles, conversations and passages remain protected. Unpublished/restricted candidates retain source restrictions and must not be inserted into an already member-readable store merely with a draft flag. A source change or access loss before publication invalidates the pending decision. After explicit publication, the independently released text follows the publication's current scope/retirement rules, while evidence access remains separately checked. World publication grants no portability to personal or other Worlds.

## Applying memory without breaking privacy [world:req:phase8-admission]
Reuse the existing context compiler and policy engine. Select a small bounded set of relevant active memories, check ownership/use scope/current source access, and admit exact versions. Broad keyword/metadata retrieval in PostgreSQL is sufficient initially; no new vector database, service per Agent or full-memory prompt dump. Active memory is clearly separated from retrieved reference data and cannot override hard policy. A stored instruction that tries to grant access or disable approvals has no executable authority.

Bind admitted versions and source dependencies to root/child jobs. Recheck before provider transmission, retry/resume, aggregation, display and effects. Correction, retirement, access loss or an applicable policy change fences affected pending work; a second toggle or permission restoration does not revive old execution. All contributing Agent dependencies matter. Retiring/correcting an ordinary preference does not alone hide completed history: historical visibility follows current privacy/source-access rules, while stale versions cannot authorize new execution or effects. Private owner memory is not inherited by a borrowed colleague's Agent or foreign organization Agent.

For private personal work, relevant authorized personal memory can be used directly. For organizational work, retain the exclusion of the full personal store. An owner can deliberately share a selected working preference through a **World-specific projection** containing only the exact approved text, use scope, version and safe provenance summary. World policy may disallow that use. The World can inspect the shared projection as effective configuration; it gains no access to the owner's remaining memories or private evidence. UI must explain that shared text may appear in organizational outputs/archives. Stop sharing invalidates future use and affected pending work, without promising to erase already shared history.

An inference drawn from an organizational transcript remains organization-derived, even when it looks like a personal preference. It cannot bypass the release process by being relabeled “personal.” Users can separately author a non-sensitive personal preference and intentionally share it, but the platform cannot prove arbitrary manually entered text contains no outside confidential facts. Organization-to-personal automation must always follow the provenance/release path.

Proposed context limits are measurable implementation choices: bounded candidate count/length, admitted memory count and serialized token budget, with explicit reasons when something is omitted. Final numbers come from the existing provider bounds and whole-phase evaluation, not an untested promise that more memory improves answers.

## Organization release and user acceptance [world:req:phase8-portability]
An authorized organization owner/admin reviews the precise proposed portable lesson, its accessible evidence and destination user. They may redact or rewrite it before release. Release binds exact text/digest, source versions, approving authority, recipient and optional acceptance deadline. User acceptance is a separate exact-version, idempotent transaction into their personal store. No duplicate copy on retries. Edits, source/evidence withdrawal or permission changes before acceptance require a fresh valid release; expired/revoked/pending releases cannot be accepted after departure.

The accepted personal record contains only the released text and a safe origin summary. Internal evidence remains World-protected; leaving never enables a source link to open restricted documents, conversations, titles or passages. A completed authorized transfer remains personal continuity after leaving. Revoking a pending release cannot silently erase an already accepted personal record. The organization retains its release/audit receipt without gaining access to other personal memories. Mandatory legal deletion/retention rules are a separate future policy decision.

Portability is available while membership/access is still valid. The leaving preview lists released lessons ready for acceptance and blocked/unreleased candidates. Offboarding can proceed without forcing an organization to approve exports; it does not become hostage to a learning review. Post-departure acceptance is excluded from this first implementation.

Organization releases and recipient acceptance can occur repeatedly during employment, independently of departure. A recipient is notified when an exact authorized portable lesson becomes available; the notice does not itself grant access to the underlying organizational evidence or bypass current acceptance authority.

## Departure and retained history [world:req:phase8-departure]
Reuse existing membership/grant/participation/Session revocation and job fences. Extend them to learning suggestions, pending release/acceptance receipts, shared preference projections, admitted memory snapshots and caches. All protected paths recheck current authority; cached UI state and late provider callbacks do not activate memory, copy lessons or create effects. A completed provider request still settles real usage even when its result is no longer publishable. Already transmitted prompts cannot be recalled.

Leaving one World does not erase personal continuity or access to another World. Organization Agents and their World memory stay with the organization; a personal Agent remains the user's. Organization chats, documents and completed records remain available to existing authorized organizational reviewers, including their established retained-review role. Private personal chats/records stay private. Completed effects are historical facts; pending approval or an old draft cannot be used as fresh authority after leaving.

The UI shows a pre-departure summary and a clear completed state: access removed, pending work stopped, accepted portable lessons retained, unaccepted lessons unavailable. Use one guarded idempotent departure command; member self-leaving versus admin-removal authority and last-owner protection must be defined and tested. No orphaned World or accidental owner removal. Permanent purge, cancellation of third-party systems and automatic account deletion are outside this phase.

## User experience and examples [world:req:phase8-examples]
Reuse dedicated Agent settings **About you/Memory**, World learning in existing Knowledge/settings surfaces, and current review/dialog primitives. Keep the workforce inspector compact. Show relevant memories used and their safe provenance through an optional details action; ordinary chat does not require opening a settings page or accepting suggestions. Restricted candidate counts, titles and previews must not leak in navigation/search. No major UI redesign.

### Adoption notices during work [world:req:phase8-adoption-notifications]
Persist the candidate before notifying, with one decision item per distinct current suggestion. Recommend a quiet inline notice or toast in the current workspace, plus a durable Notifications item so it survives reload and can be handled later. Reuse the existing Notifications entry and review/dialog patterns, with only the learning-specific delivery/storage needed here; this is not a full notification-service project. The work result and composer remain usable while the notice is ignored.

Example for an authorized personal candidate: **Suggested learning: “You prefer action lists with an owner and deadline.” — Adopt · Edit · Dismiss**. Show its intended scope and safe origin on review. Edit changes the proposed text/version before adoption; it does not remove inherited ownership/source restrictions. Dismiss leaves the suggestion inactive and suppresses repeated notices for that candidate, with its decision/history available in Memory. Ignoring a notice never activates memory automatically.

For a World candidate, notify only an eligible World owner/admin with current evidence access and offer **Review for this World**, leading to the existing exact publication decision. Do not offer personal adoption of unreleased organizational learning. For an organization-approved portable lesson, notify only its designated recipient and offer review/acceptance of the exact released text. Adoption, World publication and portable acceptance remain distinct authorized actions.

Notification summaries, previews, counters and deep links obey the same current owner/World/Session/source rules as the candidate; a notice is not an authority token. Recheck access and exact candidate/release version when opened or acted on. Revoked, expired, edited or already-decided notices cannot activate memory through old buttons, cached views or retries. Notification delivery does not widen candidate visibility, send external email, trigger an extra model call or block task completion.

Universe owns closed commands, validation and hard enforcement. World owns organization-learning/sharing/export permissions. Agent owner owns personal learning/use preferences within those boundaries. Session owns the current task and can narrow admitted memories/learning participation; it cannot permanently activate a memory or create authority just by a prompt. Any new controls/capabilities enter the existing schemas/catalogs and engine, not a second competing policy prompt. Exact new vocabulary is finalized and reviewed before code is connected.

## Whole-phase acceptance and three metrics [world:req:phase8-acceptance]
1. During ordinary work with active membership and no departure, a useful suggestion produces an authorized nonblocking notice; Adopt/Edit/Dismiss and deferred review survive reload. Ignoring or dismissing it does not activate memory, interrupt the composer or repeatedly notify for the same candidate. A saved approved preference affects a fresh authorized private Session; later feedback/correction updates future use. An unaccepted/rejected/retired memory does not. Ordinary work continues when learning is Off. Tests exercise the actual worker, not only UI state. Duplicate clicks/retries activate once; stale/edited/expired/revoked notices deny old decisions and cannot leak restricted metadata.
2. Inspect/correct/stop-use/source/history views are real, permission-safe and persistent. Exact conflicting edits fail safely; duplicate decisions/retries create no duplicate records. Restricted metadata/search/previews do not leak. A restricted-Session candidate is denied to members lacking source access; an exact authorized World publication releases only the selected text/audience, with the underlying evidence still denied. Test source/access changes racing publication and revoked publication blocking future use.
3. Organizational work excludes private personal memory. A deliberate approved preference projection works only in its named World; stopped sharing and borrowed/foreign Agent paths deny unauthorized access.
4. Exact dependency changes, revocation, resource loss and expiry fence root/child/resumed work and effects. Source access checks precede model transmission; late results cannot activate or export memory. Current retained-history visibility is preserved.
5. An authorized World owner/admin release plus designated user acceptance produces one exact personal lesson during employment, without waiting for departure. Notify only the eligible recipient of the released version; edits/revocations/expiry/stale authority reject old approvals. Accepted lessons survive leaving, without access to original organization evidence.
6. Member leave/admin removal safely revoke work/access/learning controls, preserve personal continuity and authorized organizational archives, and protect the last owner. Test concurrent departure versus activation, acceptance, aggregation and spending.
7. Freeze a varied small dataset before paid tests: preference recall/correction, irrelevant/stale memory, two-World isolation, borrowed Agent privacy, rejected and allowed portability, concealed malicious memories and late departure. Independent full-output judging defines correct workflows/total workflows and separate content criteria. Security gate pass rates are reported separately from semantic accuracy; no universal “100%” claim from a few fixtures.
8. Measure true enqueue request/acknowledgment to durable usable root result with a continuously running worker. Report human memory/export review wait separately, plus queue/model/child/retry stages and observed sampling limits. Compare matched no-memory/current-memory tasks where practical; disclose mismatches and unsupported latency claims.
9. Sum provider-reported input/output usage and estimated cost across all attempts, children and any extraction jobs, plus uncertain held charges. Report per usable result and against a declared matched baseline. Memory must justify its added context/calls with measured usefulness; no token-savings promise without evidence.

Numerical accuracy/latency targets remain undecided in the product. Required acceptance is correct authority/privacy/lifecycle behavior, independently scored stated semantic criteria and honest measurements; the user can set performance targets from the first representative results. All live implementation tests remain inside the existing cumulative US$4 cap after fresh ledger checks; pause paid proof if insufficient headroom without stopping unaffected work. Codex orchestration cost remains unknown unless the host exposes it.
