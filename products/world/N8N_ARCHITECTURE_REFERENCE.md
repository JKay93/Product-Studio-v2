# n8n reference review for World — 20 October 2026

Research and recommendations, not an approved implementation specification. Reviewed official documentation and World source at c3f8b59; no n8n runtime benchmark, account access, source extraction, service change or model-provider call. Documentation on mutable branches describes advertised behaviour, including Preview features, rather than proving deployed reliability. Some raw/GitHub caches disagreed on availability: no plan/version entitlement conclusion is made. The architecture overview itself is a short work-in-progress stub.

## Assessment

The user's environment-led distinction is useful, but the overlap is substantial. n8n documents standalone Agents as well as workflows. World should explain its intended combination of portable Agent ownership, destination-World authority, scoped knowledge and learning, collaborative Sessions and reusable deterministic Flows. A name, canvas, memory or ability to delegate is not an exclusive capability. The reviewed n8n pages do not establish an equivalent to World's whole portable-agent/destination-policy model; that is a scoped documentation observation, not proof n8n cannot implement it.

The Assistant documentation also says project access is checked on every message. Current permission checks therefore overlap too; the portable ownership/learning model and its consistent integration are the distinction to demonstrate, rather than claiming n8n relies only on prompts.

## What World actually has today

Verified in the checked-out source, supplemented by the separate installed-pilot acceptance record:

- **Typed policy enforcement:** World/owner/Session predicates, current expiry/grants/access generations, revision invalidation and source checks exist. See `World/src/modules/world-policy/index.ts:5`, migrations030:75 and031:104–193. A fully configurable resolver for every proposed namespace is not implemented.
- **Ownership and borrowing:** Agent owner identity and current destination admission/consent exist (`agents/index.ts:6`, migration031:369–370,508–516). This is not a general external Agent passport/interoperability standard.
- **Knowledge/learning boundaries:** Immutable source-version checks, memory audiences/dependencies, deliberate activation and separate release/acceptance/departure revocation exist (migrations020:36–39,032:510–566,614–615). Finite context admission cannot guarantee perfect recall.
- **Bounded Swarm:** Candidate ranking and current access/audience checks exist (migration081:119–156). Contribution history is not proven expertise; the profile's verified-capability list is empty (`agent-profile/index.ts:29–43`).
- **Composition:** Flow Agent steps enqueue governed chat jobs and retain text output; Agents discover Flow metadata and save disabled drafts (`flows/index.ts:80–87`, migrations079:130–143,086). There is no arbitrary published-Flow invocation tool in the inspected Agent tool inventory. Structured Agent-step result schemas are a gap even though deterministic action mappings/wait responses are typed.
- **Versions, approvals and cost:** Flows have immutable published definitions/pinned runs and exact approval checks (migration079:234–264,332–336). Whole-tree accounting preserves unsettled reservations (migration083:63–82). These do not imply a complete Agent promotion/rollback product lifecycle or a measured performance advantage.
- **Discovery:** Current-authority-fenced, on-demand metadata lookup exists with explicit coverage limits (migration086). Generic skill-bundle loading and a general World metadata delta protocol are not established. Config/personality snapshots and repository evaluations do not themselves provide user-facing Agent preview/publish/rollback/evaluation releases.

## Proposed priorities

1. **Complete the Agent–Flow contract.** Typed requests/results, one governed execution receipt, explicit callable Flow permissions, execution links and context/session selection. Authoring and executing a Flow need distinct grants. Deterministic actions continue without a model; judgment steps can invoke an eligible Agent.
2. **Improve the operating experience around existing execution.** Inspect inputs/outputs, map fields, select accounts securely, diagnose blocked steps and review changes before publication. Prefer a few reusable business modules over more hardcoded vertical pilots.
3. **Add small, fresh environment context.** A code-produced manifest of permitted resources, available collaborators and relevant state changes; retrieve detail on demand. Current access checks still run at every sensitive retrieval/action, regardless of cached metadata. Measure input tokens, quality and latency before adopting a larger context protocol.
4. **Introduce controlled Agent releases when shared usage needs them.** Preview, compare and promote a configuration; retain effective versions in run evidence and support deliberate rollback. Current access must still be rechecked at subsequent governed boundaries; publishing an old configuration cannot revive revoked access or retroactively change completed actions.
5. **Later capability bundles and behavioural release checks.** Bundle task guidance with authorised tools internally, without requiring SMEs to understand a Skills interface. The earlier decision to defer that UI still holds. Expand model evaluations only with explicit spending authority and authorised representative data.

These are research recommendations, not approved tasks. No reset or engine replacement is justified by this review. World should keep the Universe/World/Agent/Session ownership model and strengthen the existing runtime and Flow foundation. n8n provides useful references for many of those mechanisms; claims that World is faster, cheaper, safer or more accurate still require comparable measurements.
